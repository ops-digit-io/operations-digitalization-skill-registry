# Operations Digitalization — Skill Registry

The repeatable procedures of **MPEE Operations Digitalization (OD)** at OESL, written as
loadable [Agent Skills](https://code.claude.com/docs/en/skills) and indexed so a person or
an agent can find the right one without reading the whole department.

Derived from the [`ops-knowledge-graph`](https://github.com/ops-digit-io/ops-knowledge-graph)
bundle — specifically its **skill map** (the four (now retired) service lines' own skills, tasks,
playbooks, metrics and agent briefs) and the **Operations Digitalization department map**
(the department OS core, the smart-factory module, and the `10-Department` practices).
Nothing here was invented; see [`docs/derivation.md`](docs/derivation.md) for the
concept-by-concept trace.

> **Scope note.** The **Digital Unit** material in the knowledge graph is deliberately
> excluded. The Digital Unit will be a new department; this registry describes Operations
> Digitalization as it works today.

**Process map and downloads.** Live at <https://ops-digit-io.github.io/operations-digitalization-skill-registry/>. The new-state process flow with every skill on its step is built as a static site: `python scripts/build_site.py` (output `site/`, opens from the file system, built on every push by CI as an artifact). Pick a lane and a step, open a skill, download a lane or a single skill as a spec-conformant `.zip`. The same mapping as a table: [`docs/new-state-skill-map.md`](docs/new-state-skill-map.md); the data: [`docs/new-state/process.yaml`](docs/new-state/process.yaml); the specification and how it is met: [`docs/agent-skills-spec.md`](docs/agent-skills-spec.md). Publishing and the Pages setup: see that page.

**[See the process overview](docs/process-overview.html)** — historical: the four service lanes the new state retires, as a BPMN-style flow (steps, error-path gateways, wait states, hand-offs between lanes) with every skill attached to the step it serves. Open the file in a browser; it is generated by `scripts/build_process_overview.py`.

## Two libraries: core and extension

**Core = the skills on the owner's process flow** ([`OD_NewState_ProcessFlow.html`](docs/new-state/OD_NewState_ProcessFlow.html), new-state service lanes with skills & gaps): every skill drawn on one of its steps, under the name it has there, plus the net-new builds it lists, now built and placed on their steps (`catalog-usecase`, `catalog-systems`, `catalog-guardrails`, `deploy-appstore`, `it-demand-package`, `od-prototype-poc`, `od-capital-request`). The same flow as data is [`process.yaml`](docs/new-state/process.yaml), as a diagram [`OD_NewState_Flow.mermaid`](docs/new-state/OD_NewState_Flow.mermaid); `scripts/validate_registry.py` fails if core and flow disagree. **Extension = everything else**: skills that deepen a step (listed as `proposed` on it) or cover a neighbouring process. Every skill requires `od-context`.

## How to use it

**As a person.** Start at `od-context`, then open the lane you are in. The practice skills
are the steps its playbook points at.

**As an agent.** Load `od-context` first — every other skill declares it in
`metadata.requires` and the validator enforces it. Then load the lane or practice skill for
the work in hand; each declares what it composes with.

**In a Claude Code project**, symlink or copy the skills into the skills directory:

```bash
mkdir -p .claude/skills
for s in skills/*/; do ln -sfn "$(pwd)/$s" ".claude/skills/$(basename "$s")"; done
```

## The data path, in one line

```
PLC ──(one of three ingress variants)──► IIoT Edge Platform ──MQTT──► Node-RED
                                                 └── offload ──► Databricks ──► Azure Storage Account (Parquet)
```

**Databricks** is the data platform the IIoT Edge Platform offloads through, the target is an
**Azure Storage Account**, and the main file format is **Parquet**. Anything that reads
shopfloor history reads from there.

**Global platform, local dashboards.** Databricks and the storage account are the global
layer. **Grafana is a local instance per plant**, building that plant's manufacturing
dashboards from that plant's data. A line-side dashboard belongs on the local instance; a
cross-plant question belongs on the global platform.

> The source decks still name an **MDL** and treat **ContiTech** as a shared-services partner
> and standing constraint. **Neither is used.** Both were removed here and in the knowledge
> bundle; the raw exports under `90-Sources/` are never hand-edited, so they still say the old
> thing — see [`docs/derivation.md`](docs/derivation.md) § *Where this registry deliberately
> contradicts the bundle* before regenerating anything.

## What the skills are opinionated about

The registry inherits the department's own rules rather than inventing house style. The
four that change answers most often:

1. **Tracked is not proven.** Tracked and finance-proven savings are both true
   about the same portfolio. They are never added together.
2. **Built is not handed over, and handed over is not in use.** `IMPLEMENTED` and
   `PRODUCTIVE` fail separately, which is why handover has its own tracked state.
3. **Absence is not a zero.** Many use cases carry `UNKNOWN` priority and many
   saving rows carry no reliability. Reading those as "low" is the most frequent way to be
   wrong about this portfolio.
4. **No figure without a nameable source and a read date**, and no invented figure at all —
   open questions stay `⟨… — to confirm⟩`.

## No company figures in skills

Skills carry guidance and process, not data. They do not state current counts, spend,
savings, per-plant status or dated snapshots of the company; they say which live source holds
the figure and how to read it. `scripts/check_no_figures.py` lists lines that look like
such figures (heuristic, read-only). `registry.yaml` keeps the three provenance dates
`data_as_of`, `graph_as_of` and `flows_as_of` for the sources the skills were derived from.

## Verification status

**Unverified.** The skills were drafted from the knowledge bundle; nobody has read them
line by line against the source systems. That matches the bundle's own trust statement and
is stated rather than glossed. The open gaps the department has not yet closed are listed
in `registry.yaml` under `open_gaps` and appear as `⟨…⟩` in the skills themselves.

## Format

This registry is two things at once, and both are checked:

- a library of **[Agent Skills](https://agentskills.io)** — one `SKILL.md` per skill, with
  `references/`, `assets/` and `scripts/` beside it;
- an **[Open Knowledge Format](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing)
  v0.2 bundle** — the same directory of Markdown files, readable as a knowledge graph by
  anything that speaks OKF, including the `ops-knowledge-graph` bundle these were derived from.

They conflict in exactly one place: OKF wants `type` and `title` at the top of the file, and
the Agent Skills spec allows only six top-level keys in a `SKILL.md` — anything else makes
packaging and upload fail with a hard error. So a skill carries its OKF fields under
`metadata.okf`, which the spec reserves for exactly this purpose; every other concept carries
ordinary top-level frontmatter. The contract, the type vocabulary and the identity rules are
in [`docs/okf-conventions.md`](docs/okf-conventions.md).

## Repository layout

```
registry.yaml                    machine-readable index: tiers, owners, authority levels, open gaps
skills/<skill-id>/SKILL.md       one core skill (named by the New-State process files)
skills/<skill-id>/references/    supporting material, assets/ and scripts/ beside it
skills-extension/<skill-id>/     one extension skill, same layout
docs/skill-map.md                the four lanes' skills/tools/interfaces, consolidated
docs/derivation.md               concept-by-concept trace back to the knowledge graph
docs/skill-state-map.md          generated Mermaid map: every skill, its lane, its build state, what is next
docs/vault-alignment.md          crosswalk against the department's own skill-map plan and gap analysis, and the resulting build order
docs/okf-conventions.md          the OKF contract, its three deviations, and what the guard refuses
index.md, */index.md             generated OKF directory indexes (OKF §8)
log.md                           bundle history (OKF §9)
scripts/skillpaths.py            where the skills live: core and extension library, one helper for every script
scripts/check_no_figures.py      lists lines in skills that look like company figures (heuristic, read-only)
scripts/validate_registry.py     guard: registry ↔ folders ↔ frontmatter ↔ cross-references
scripts/verify_okf.py            guard: the OKF contract
scripts/build_okf_index.py       regenerates the directory indexes
scripts/build_skill_map.py       regenerates the skill state map
scripts/build_new_state_skill_map.py  regenerates docs/new-state-skill-map.md from docs/new-state/process.yaml
scripts/agent_skills_spec.py     checks every skill against the open Agent Skills specification; --export writes spec-strict packages
scripts/build_site.py            builds the static documentation site: process map, skill pages, specification page, downloads
```

## Validating a change

```bash
pip install pyyaml
python3 scripts/validate_registry.py       # registry.yaml and the skill frontmatter agree
python3 scripts/verify_okf.py              # the OKF contract
python3 scripts/build_okf_index.py --check # the generated indexes are current
python3 scripts/build_skill_map.py --check # the skill state map is current
python3 scripts/build_process_overview.py --check
python3 scripts/build_new_state_skill_map.py --check
python3 scripts/agent_skills_spec.py --export dist/skills   # strict export must be spec-valid
pip install markdown && python3 scripts/build_site.py       # the documentation site
```

Run the generators in this order after a change: `build_okf_index.py`, then `build_skill_map.py`, then `build_process_overview.py`.

It checks that every folder has a registry entry and vice versa, that frontmatter parses,
that each `name` and `metadata.id` matches its directory, that descriptions are substantial
enough to trigger on, that tiers agree between the two, that every `od`-scoped skill
requires `od-context` while a `portable` one instead ships a real `od_integration` note, and
that no `requires` or `composes` points at a skill that does not exist.

`verify_okf.py` checks that every concept's frontmatter parses and declares a known `type`,
that a `SKILL.md` carries only the six spec-allowed top-level keys and its OKF fields under
`metadata.okf`, that every other `title` slugs to its filename, that `generated` names an OKF
actor and an ISO timestamp, that every `resource`, path-shaped `derived_from` entry and
in-bundle link resolves, and that no wikilink or bundle-relative link has crept in.

When a source concept changes, follow "Keeping this registry true" in
[`docs/derivation.md`](docs/derivation.md).
